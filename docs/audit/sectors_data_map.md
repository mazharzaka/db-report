## 1. ملخص تنفيذي (Executive Summary)

تم إعداد هذا التقرير المرجعي كوثيقة توثيقية وهندسية شاملة (Read-Only Architecture & Data Map) بهدف حسم الفروق البنيوية وطرق استخراج الإيرادات والمبيعات عبر مختلف قطاعات دريم بارك المتاحة داخل قاعدة البيانات المركزية `[dbDream_Park_Resturant]`.

### النتائج الأساسية للاستكشاف (Key Architectural Findings):
1. **طبيعة جدول الفروع `[dbo].[Branchs]`:**
   يحتوي الجدول على **60 منفذاً** مصنفة عبر عمود `[Type]` إلى 6 قطاعات تشغيلية:
   - **`Type = 1` (المطاعم - Restaurants & F&B):** 13 فرعاً ومطعماً رئيساً.
   - **`Type = 2` (الألعاب الترفيهية الكبرى - Major Amusement Rides):** 8 نقاط تشغيل / كاشيرات مركزية للألعاب.
   - **`Type = 3` (الفيديو جيم والواقع الافتراضي - Video Games & VR & Kids Zones):** 6 مناطق وصالات ألعاب.
   - **`Type = 4` (الكرفانات والأكشاك - Caravans & Kiosks):** 27 كرفاناً ومنفذ بيع سريع منتشرة في الحديقة.
   - **`Type = 5` (بوابات التذاكر - Ticket Gates):** 4 منافذ لتذاكر الدخول الفضية والمبيعات.
   - **`Type = 6` (الأمانات والانتظار - Lockers & Parking):** منفذان لبارك السيارات والأمانات.

2. **الفارق الجوهري في "وحدة القياس" (Unit of Measurement):**
   - **في المطاعم (`Type = 1`) والكرفانات (`Type = 4`):** يمثل كود الفرع `Branch_Code` منفذاً جغرافياً ومالياً مستقلاً بذاته يبيع أصناف أطعمة/مشروبات/بضائع.
   - **في الألعاب (`Type = 2`) والفيديو جيم (`Type = 3`):** كود الفرع `Branch_Code` **لا يمثل لعبة واحدة**، بل يمثل **نقطة بيع / كاشير مركزي (POS Cashier Station)** تُقطع من خلاله تذاكر لعدة ألعاب ترفيهية مختلفة تماماً (مثال: كاشير `111 - rocket` يقطع تذاكر لكل من: *قطار الموت، الصاروخ، ليزر زون، الرماية 2*).

3. **حقيقة الفيو المالي `[dbo].[Rpt_Pos_max]` مقابل `[dbo].[POS_Post]` و `[dbo].[Pos_item_post]`:**
   - جدول/فيو `Rpt_Pos_max` صُمم تاريخياً ليخدم تصنيفات المطاعم ومبيعات الأغذية والمشروبات (`total_Food`, `total_Bev`).
   - عند محاولة قراءة مبيعات الألعاب (`Type = 2`) أو الفيديو جيم (`Type = 3`) من `Rpt_Pos_max`، **يحدث انهيار في الأرقام وتظهر فقط كسور ضئيلة جداً من الإيراد الفعلي** (مثال مثبت بالدليل المالي: كاشير الصاروخ `111` حقق في يوم 19-11-2026 إيراداً حقيقياً قدره **116,570 ج.م**، بينما أظهر `Rpt_Pos_max` فقط **14,315 ج.م**!).
   - علاوة على ذلك، فإن `Rpt_Pos_max` يعتمد على `LEFT JOIN` مع جدول `dateday`، مما يتسبب في إرجاع **صفر (0)** لأي منافذ جديدة أو غير مسجلة في جدول الأيام (مثل كرفان `1029 - Funny` وكرفان `1030 - altaawws` ومطعم `14 - Canteen`).
   - **القرار الهندسي المعتمد:** مصدر الحقيقة المالية المطلق للإيرادات المالية المجمعة هو **`[dbo].[POS_Post]`**، ومصدر الحقيقة لحركة وتفصيل الألعاب والأصناف هو **`[dbo].[Pos_item_post]`** (أو جدوله الأساسي `[dbo].[POS_Sub_post]`).

## 2. تحليل الكود الحالي في مشروع `caravan-revenues-app`

من خلال الفحص الدقيق لملفات الـ Backend (`services/caravanReportService.js`، `services/caravanItemService.js`، `server.js`) والـ Frontend (`page.tsx`، `useCaravanDashboard.ts`، `DailyRevenueMatrix.tsx`)، تم استخراج القواعد التي يعمل بها الكود حالياً:

### 2.1 مستوى الإيرادات التجميعية والمالية (Financial Aggregations)
- **الجدول المعتمد:** `[dbo].[POS_Post]` مع ربطه بجدول `[dbo].[Branchs]`.
- **لماذا لا يستخدم الكود `Rpt_Pos_max`؟**
  الكود يستبعد تماماً الاعتماد على `Rpt_Pos_max`؛ لأن `POS_Post` هو جدول المعاملات التجميعية الفعلي الذي يحتوي على:
  - `Cash` (المتحصلات النقدية).
  - `Visa` + `Visa2` + `Visa3` (متحصلات البطاقات الائتمانية).
  - `[C/L]` (الآجل وضيافة الشركات).
  - `NetOfInv` (الإجمالي الصافي الشامل للضريبة المطلوب تحصيله).
  - `TotalInv` (قيمة الفاتورة قبل الضريبة).
  - `Sels_Tax` (ضريبة القيمة المضافة 14%).
- **شروط التصفية (Where Clause):**
  ```sql
  WHERE b.[Type] = 4
    AND p.[Doc_Date] >= CAST(@startDate AS DATE)
    AND p.[Doc_Date] < DATEADD(DAY, 1, CAST(@endDate AS DATE))
  ```
- **استبعاد الملغي واسترجاع المرتجعات:**
  الكود يربط جدول المرتجعات `[dbo].[Pos_item_post_void]` عبر `OUTER APPLY` على مستوى كل منفذ وفترة لحساب إجمالي المرتجعات (`TotalVoids`) وعددها (`VoidCount`).

### 2.2 مستوى تفاصيل وحركة الأصناف (Operational Items Analytics)
- **الجدول المعتمد:** `[dbo].[Pos_item_post]` (وهو فيو يجمع بين `POS_Sub_post` و `POS_Post` و `items` و `Groupitem`).
- **متى ينزل الكود لمستوى `Pos_item_post`؟**
  ينزل الكود لمستوى الأصناف في الـ Endpoint:
  `/api/reports/caravans/items-summary`
  المسؤول عن استخراج:
  1. الأصناف الأكثر مبيعاً (Top 5 Best Sellers) والأصناف الراكدة (Dead Stock / Slow Moving).
  2. مقارنة صنفين متنافسين (Head-to-Head Duel).
  3. تحليل مبيعات بوابات الحديقة لتقدير عدد الزوار (`guests = ticketQty / divisor`).
- **المعادلات وشروط التجميع:**
  - القيمة المالية للصنف: `SUM(p.[Item_Qunt] * p.[Item_Price])`.
  - الكمية المباعة: `SUM(p.[Item_Qunt])`.
  - شرط استبعاد الملغي: يتم تلقائياً داخل الفيو عبر `(ISNULL(p.[Void_item], 0) = 0)`.

## 6. قواعد التوجيه الذكية لمحرك الاستعلامات (Routing Rules for `sqlQueryEngine`)

هذه القواعد مُعدة ومصاغة لتضمينها مباشرة داخل الـ **System Prompt** والـ **Glossary** الخاص بموديل الذكاء الاصطناعي (`sqlQueryEngine`) لضمان عدم الخلط وتوليد كود SQL دقيق من أول محاولة:

```markdown
### DREAM PARK SQL GENERATION & ROUTING DIRECTIVES

1. [SECTOR CLASSIFICATION VIA BRANCHS.TYPE]:
   - Type = 1 -> Restaurants & Main F&B (المطاعم وصالات الطعام)
   - Type = 2 -> Major Amusement Rides (الألعاب الترفيهية الكبرى)
   - Type = 3 -> Video Games, VR, Arcades & Kids Zones (الفيديو جيم والواقع الافتراضي وألعاب الأطفال)
   - Type = 4 -> Caravans & Kiosks (الكرفانات والأكشاك ومنافذ البيع السريعة)
   - Type = 5 -> Gate Ticketing (تذاكر الدخول)
   - Type = 6 -> Parking & Lockers (البارك والأمانات)

2. [TABLE ROUTING LOGIC]:
   - NEVER query [Rpt_Pos_max] for Amusement Rides (Type=2) or Video Games/VR (Type=3); it underreports their revenues by up to 90%.
   - For Branch/Outlet-level Daily/Monthly Financials (Cash, Visa, C/L, Gross Total, Tax):
     ALWAYS use [dbo].[POS_Post] p INNER JOIN [dbo].[Branchs] b ON p.[Branch_Code] = b.[Code].
     Total Revenue = ISNULL(p.[NetOfInv], 0) [or Cash + Visa + CL].
     Ensure condition: (p.[Void] = 0 OR p.[Void] IS NULL).
   - For Item-level, Game-level, or Best/Slow Sellers:
     ALWAYS use [dbo].[Pos_item_post] p (or [dbo].[POS_Sub_post]).
     Item Gross Value = SUM(p.[Item_Qunt] * p.[Item_Price] * (1.0 + ISNULL(p.[item_Sels_Tax_P], 0)/100.0)).
     Ensure condition: ISNULL(p.[Void_item], 0) = 0.

3. [CRITICAL: AMUSEMENT & VR GAME QUERIES]:
   - When the user asks for the revenue of a SPECIFIC GAME by name (e.g., "إيراد القطار", "مبيعات الصاروخ", "لعبة ديسكفري", "VR 360", "الموفى", "شلال المرح"):
     DO NOT filter by Branch_Code alone! Multiple rides are sold from the same cashier terminal.
     MUST query [dbo].[Pos_item_post] and filter/group by p.[item_name] or p.[item_Code].
     Example:
     ```sql
     SELECT 
         p.[item_name] AS [Game_Name],
         SUM(p.[Item_Qunt]) AS [Tickets_Sold],
         ROUND(SUM(p.[Item_Qunt] * p.[Item_Price] * (1.0 + ISNULL(p.[item_Sels_Tax_P], 0)/100.0)), 2) AS [Gross_Revenue]
     FROM [dbo].[Pos_item_post] p WITH (NOLOCK)
     INNER JOIN [dbo].[Branchs] b WITH (NOLOCK) ON p.[Branch_Code] = b.[Code]
     WHERE b.[Type] IN (2, 3)
       AND p.[item_name] LIKE '%القطار%'
       AND p.[Doc_Date] >= @startDate AND p.[Doc_Date] < DATEADD(DAY, 1, @endDate)
       AND ISNULL(p.[Void_item], 0) = 0
     GROUP BY p.[item_name]
     ORDER BY [Gross_Revenue] DESC;
     ```

4. [CARAVAN & RESTAURANT QUERIES]:
   - If asked about "كرفان" (Caravan), filter by b.[Type] = 4.
   - If asked about "مطعم" (Restaurant), filter by b.[Type] = 1.
   - If asked about "مبيعات كرفان X بالأصناف", join [POS_Sub_post] with [Branchs] WHERE b.[Type] = 4 AND b.[Code] = X.

5. [TAX & NET ACCOUNTING FORMULAS]:
   - Gross Revenue (شامل الضريبة) = NetOfInv = Cash + Visa + CL.
   - Net Sales (قبل الضريبة) = Gross Revenue / 1.14.
   - VAT 14% (ضريبة القيمة المضافة) = Gross Revenue - Net Sales.
